版本号体系

26R3.1 是怎么读出来的

平台版本号采用四段格式 {Year}R{Release}.{Patch}.{Maintenance}，另有与版本号解耦的 build 号。

年度与版本位

「26R3」表示 2026 年第 3 个正式版本，如 26R3.1 的「26R3」。

Patch 位

正式版本内的小版本位，如 26R3.1 的「.1」。

Maintenance 位

维护发布序号，按 scope 独立递增（如 26R3.1.46），不同 scope 的维护版本各自编号，故版本号并非严格时间顺序。

build 号

与版本号解耦的十进制数字串（如 Assembly 13258 / Platform 13250），由构建工件产出，供定位具体构建。

Vault Information 里能看到什么 每个 Vault 在 Vault Information 页只读展示三个版本标识：Vault Version（当前版本号）、Vault Assembly Version（组装 build 号）与 Vault Platform Version（平台内核 build 号）。三者仅供查看与排障，不可自行选择。
发布类型

三类发布

按内容与节奏区分三类发布。

公开发布（General Release）

带来新功能与修复的正式版本，如 26R3.1。每个公开发布都有对应的发布说明：新功能、已修复问题与已知问题。

维护发布（Maintenance Release）

针对已发布版本的小修复，版本号 Maintenance 位递增。

预发布（Prerelease）

正式发布前，在沙盒上运行新版本以验证配置与流程的窗口。详见「预发布 FAQ」。

发布流程

一个版本如何发布

版本经由发布列车（ADCV）统一编排，关键节点如下。

01
发布列车收敛

功能与配置在发布列车（ADCV）上收敛，形成目标版本。

02
切版与打标

切出版本并打标（如 v26R3.1-13258），版本号与 build 号从此确定。

03
制品产出

产出镜像与 CLI / 演示制品，供环境部署与客户端使用。

04
环境升级

沙盒可先行验证，生产 Vault 由平台统一编排升级。

版本升级规则

版本由平台统一管理

以下规则保证升级可预期、可追溯。

客户不挑版本

生产 Vault 的升级由平台统一编排，不能提前升级、延后升级、跳过或降级。

沙盒版本方向

目标版本等于源版本：直接复制；目标更高：复制后前向升级；目标更低：拒绝（不会误降级）。

沙盒载荷二选一

仅配置载荷：复制配置，不含业务数据、文档与用户；含数据载荷：源沙盒的完整拷贝（含用户与归属）。

派生后相互独立

沙盒与源互为独立实例：源的后续变更不影响沙盒，沙盒的变更也不回流源。

发布建议

升级期间的几点建议

沙盒先行验证

正式升级前，先在沙盒上运行新版本，验证既有配置与关键流程。

升级窗口内不建议配置变更

避免配置变更与版本升级相互影响。

关注已知问题

升级前查看当前版本的已知问题页。

想深入了解？

查看帮助中心的操作文档，或申请试用体验 26R3.1。
